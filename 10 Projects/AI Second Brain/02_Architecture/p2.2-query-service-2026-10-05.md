# P2.2 query service: first runs with a local model

**Result (run B, the one that counts):** the scoped query service answers end to end on the Air with a local model and the network blocked. It **misses the D56 text target by about 5×** (p95 42.1 s against < 8 s; p50 23.4 s, n=20). One answer was confidently wrong, and the service's own checks could not catch it. A second answer was cut off at the token cap and is now reported as a failure rather than graded. Measured per [[90 System/briefs/P2.2|P2.2]] condition 5. Since David's Q9 answer (5 Oct) the Air **is** the inference host until the D53 purchase, so this miss is on the host actually in use. It is still not acceptance: one model, one machine under normal desktop load, and no sustained or always-on numbers, which Q9 leaves for the dedicated host.

Draft per David's Q7 answer (2 Oct): he confirms it later. Raw data stays outside the vault.

Its figures (p50 20.3 s, p95 27.9 s, server peak 4.79 GiB) are kept below for the record only. **The two runs are not comparable:** different corpus, a different latency definition, and stricter response parsing in B.

- Nearest-rank percentiles. The runs computed rank with `round`, which is not strictly nearest-rank; recomputed from the stored per-case times with the corrected `ceil`, every figure here is unchanged. With n=10 a pass's p95 is its maximum; pooled, it is the 19th of 20 values. Both maxima are the truncated `write_approval` case (42.1 s and 58.8 s), so the tail is mostly one case running to the token cap.
- **End-to-end = the wall clock of one complete query** (index, retrieval and model in the same call). Run A summed model time from one execution with index and retrieval times from another (round C, finding 6).
- **Peak memory, model server: 4.14 GiB RSS** (4,345,632 KiB), sampled every 0.25 s across both passes (1,809 samples). The 1 Oct benchmark reported 3.30 / 3.35 GiB for its two candidates. Run A's note said 1 Oct had no server figure, which was wrong. It is one process on one model, not a host-sizing answer for D53.
- Compared with 1 Oct (median 6.4 s): that run sent shorter supplied excerpts and capped output at 220 tokens. The gap is **not diagnosed**: the server log records prompt-processing and generation times per request, but they were not analysed separately.

## What this shows

1. **`supported` is never returned, by design.** The code reports `supported` only when an entailment verifier confirms the answer, and none exists yet (T4.1). David confirmed on 5 Oct (Q21) that it stays this strict until T4.1: every answer still shows its citations and why it is not `supported`.
2. **The lexical grounding check cannot catch a plausible wrong answer.** `source_retention` was wrong in both runs, with different wrong answers. Retrieval missed the right chunk and the model filled the gap from a neighbouring one.
3. **Decline detection fails in both directions.** It missed two real declines (French; "does not specify") and fired on a correct answer that began with a hedge. The phrase list was **not** tuned to fit these cases: tuning a heuristic on the dev set would make the dev set useless for measuring it. Input for P2.1 / T4.1.
4. **Abstention rests on the model, not on retrieval.** Retrieval returned near-miss evidence for both unanswerable questions; the model declined both in substance.
5. **320 tokens is too tight for at least one case.** The cap was kept for comparability with run A. Raising it is a change to the request version and needs its own run.

## Fixed during the runs

- **Run A, first pass:** the adapter sent a raw prompt to llama.cpp's `/completion` endpoint, with no chat template and no end-of-turn, and the model looped until the token cap. It now uses `/v1/chat/completions` with thinking off. That pre-fix pass stored no answer text, so the looping is attested only by the lead's own observation and the pre-fix RSS log.
- **Before run B (round C fixes):** corpus pinned to the three files; response parsing now fails loudly on an error object, missing or non-text content, a truncated generation or an unterminated `<think>` block; the request version now covers the whole request shape; latency is measured in a single execution; output writes walk their parent directories without following symlinks.

**Observations to analyse later, not findings:**
- The step change after the first few requests reproduces in the sweep. Load averages before configs ranged from about 3 to 33 (other processes, including this session's own tests), and `pmset -g therm` records nothing on this Mac, so **throttling versus contention is unresolved**.
- The GPU is doing the work (CPU-only is about 3× slower). Flash attention, larger batches and 8 threads make no visible difference within the drift between baselines.
- `write_approval` is still cut off at 640 tokens, so the cap is not simply too tight; **looping is suspected, not shown**, because neither the report nor the server log keeps the truncated text. With 2 or 3 chunks it answers.
- Fewer chunks is the only lever that moved latency (2 chunks: p50 15.2 s, p95 23.6 s). It **changes the verdicts, not demonstrably the quality**: with 2 chunks `query_navigation` gets a correct direct answer ("read `index.md` first") instead of a decline; `unknown_password` still declines in substance, but in words the decline list misses, so it is graded `incomplete`; `source_retention` is wrong with 4 chunks and with 2. Whether fewer chunks costs quality needs the per-case review, on more than 10 cases.
- Still far from D56 (p95 < 8 s) on this Air, under any setting tried.

**To resume:** controlled-load rerun (quiet machine, longer cool-downs, `powermetrics` if David allows sudo); per-case quality review of chunks-2/3; why `write_approval` loops.

## Network blocked: condition 4, second half
