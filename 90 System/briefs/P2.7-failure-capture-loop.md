# A self-improving loop for Ask Brain: capture failures, resolve them, prove the fix

## Goal (one sentence)
Every question the phone fails on is captured, then either answered by David once or resolved by an agent, and it comes back as a regression case, so each real failure improves the system and the score proves it.

## Why
- Review rounds 5–18 on phone dates were driven by wordings that Codex *imagined*. Real failures from David's own use are a better test set, and they cost no review round to find.
- This is the product's point (project instructions: the evaluation and governance layer is the product): a visible loop from failure to measured fix is what a client would want to see running.
- Today's traces keep only a hash and the length of each question (`question_sha256`, `question_chars`), by design. The loop needs the question text, so it is a **data-policy decision**, not only a build task.

## The loop (target design)
1. **Capture.** On every question the service records a failure *signal*: no date read although the text looks date-like; status `incomplete` or a decline; an `unclear` ask-again; a timeout; later, David's one-tap "wrong" on the phone. Question text and answer go to a local failure store on the Air, outside the vault and outside git, readable only by the local model and by David.
2. **Triage.** The local model groups failures by class (date, term not in the note, retrieval miss, wrong note, decline, latency), on demand or weekly. Cowork lists them from the digest; nothing is fixed at this step.
3. **Resolve, one of two paths:**
   - **Ask David** (the "pause la question" path; he sees the real text, agents never do) when the answer needs knowledge only he has (for example a term that is not in a minimised note): one question, one answer, stored as an alias or a note proposal that he fact-checks before it enters the vault.
   - **Agent path** when the cause is in the system: Claude Code proposes the change to retrieval, prompt or parser from the **class and the synthetic equivalent**, Codex reviews it under the existing review tiers.
4. **Prove.** The failure's **synthetic equivalent**, never the original text, becomes a regression case (P2.5 layer 1 test set, P2.6 phrase set), and only after it passed the leak check (decision 4). Cases are split: a tuning pool and a **held-out half that no change touches**. A fix counts only if the score improves on the pool and does not drop on the held-out half.
5. **Ship** through the normal commit and push. The failure is closed with a link to its case and its score change.

## Design decisions (David, 7 Oct 18:15, via Cowork)
1. **Who sees the question text: the local model only.** No cloud model, agent or reviewer (Claude Code, Codex, Cowork) reads raw question text. *Consequence (Cowork's design, to confirm):* a local-model step turns each failure into a **class label plus a synthetic equivalent** (the same kind of question, with no names, children or places). Cloud agents work from the class and the synthetic equivalent, never from the real text. David reads the real text himself, on the phone or the Mac.
2. **Retention: 90 days** for unapproved failures. A failure David approves as a test case is kept as its synthetic equivalent, not as the original.
3. **Review: weekly, scheduled. Stands (David, 8 Oct 16:02).** A weekly review reads only the local model's digest (counts, classes, signals, synthetic equivalents that passed the leak check), never the raw text. Scheduled task "Weekly failure review", Fridays 15:55 (Brussels); until capture exists it only reports the stage P2.7 has reached. Once capture exists it also reports, from the audit log only: leak-check passes and flags, David's approvals and rejections, and whether the 90-day deletion ran.
4. **Leak check on synthetic equivalents: option B (David, 8 Oct 16:02).** The local model's synthetic equivalent is not trusted on its own (T9 showed small models misattributing evidence). A deterministic check, in code, compares each synthetic equivalent with its original: any shared name, capitalised word, number, date, place or rare word (exact list fixed in the build brief, Codex-reviewed) **flags** it. A flagged item goes to David, who approves, rewrites or rejects it, and reaches no cloud agent until he has. An unflagged item goes into the digest. Rejected: A (David approves every item: safest but friction) and C (trust the local model: one bad anonymisation sends personal text to the cloud). The check is tested with planted leaks before any real failure is captured, and its flag rate is reported weekly so it can be tightened.
5. **Model and audit logs are kept and available for review and audit (David, 8 Oct 16:02).** See "Audit trail" below.

**Leak-check rules (decision 4: the exact list, for Codex review; revised after review round 1).** Text is compared after Unicode NFKC, lower-casing and accent folding ("Léo" = "leo"); tokens are runs of letters or digits. The synthetic equivalent is **flagged** if any rule hits:
1. **Shared capitalised word:** a word capitalised anywhere in the original (sentence-initial words included) that appears in the synthetic.
2. **Shared number:** any digit sequence of the original appearing in the synthetic.
3. **Date text in the synthetic:** anything the service's date reader finds (`serve.resolve_dates`), **resolved or not** (so "morgen", "demain", "tomorrow" all count); any month or weekday name, and any relative-day word (EN, FR, NL), in the synthetic.
4. **Shared uncommon word:** a shared word **of any length** that is not on the common-word list (two-letter names such as "li" or "bo" count). The list holds **function words only** (articles, pronouns, prepositions, conjunctions, auxiliaries and question words of English, French and Dutch), **no domain or activity words**: "climbing", "school", "menu" count as uncommon. The full list is in `leakcheck.py` and is reviewed with stage L's code; adding a word is a reviewed change.
5. **Contact patterns in the synthetic**, shared or not: an e-mail address, a URL, a phone-number-like digit run (7 or more digits with spaces, dots or dashes).
6. **Near-copy:** the synthetic shares 60 % or more of the original's tokens (Jaccard on word sets).

Any hit flags the item; the rules hit are recorded (rule numbers only, never the words). **Planted cases the tests must flag** include, at least: a capitalised name; a lowercase name and its accent-folded form (`quel sac pour léo` → `does leo need a bag`); a short place (`wat meenemen naar spa` → `what is needed in spa`); two-letter lowercase names (`what bag for li` → `does li need a backpack`; `quel sac pour bo` → `does bo need a backpack`); a child's activity (`what must my child bring for climbing` → `which equipment is needed for climbing`); a date resolved and unresolved, in EN, FR and NL (`prepare my bag tomorrow` → `wat meenemen morgen`); a number; an e-mail and a phone number. **Clean pairs that must pass** include rewrites sharing only function words. The check errs on the side of flagging: a flagged item costs David one look; a missed leak sends personal text to the cloud.
